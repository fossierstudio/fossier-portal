# Decision log

## Run the portal beside k3s, not inside it

The host's k3s cluster runs the Canopy dev environment. Adding the portal to it
would put a shared API server and shared resources at risk for a tool that
doesn't need them yet.

The portal runs as its own Compose project with memory and CPU limits instead.
It can be stopped, rebuilt, or removed without touching that cluster.

## Build the image on the host

The first version built the image on a workstation and shipped it to the host,
because the host also runs CI builds that once filled its disk. The workstation
ran short of disk instead, while the host now has room to spare, so
[`deploy/deploy.sh`](../deploy/deploy.sh) sends the source to the host and
builds there. A build takes a few minutes of CPU that CI jobs then share. The
previous image stays tagged for rollback, and the Dockerfile is multi-stage, so
any machine with Docker can produce the same image.

## Keep catalog data in this repo

Backstage usually reads a `catalog-info.yaml` from each service's repo. Several
of these repos are private, and this one is public, so catalog entries live here
and link to public pages. Component View Source links open the definition here,
and systems link to it instead, because TechDocs would otherwise fetch their docs
from GitHub through `backstage.io/source-location`. Without access to those repos, the portal needs no
GitHub token, which also means there is no credential to protect.

The cost is that an entry can drift from its repo. Moving entries into each repo
comes with live CI status, which needs a token anyway.

## Run TechDocs inside the container

The default TechDocs setup starts a Docker container for each build, which would
mean giving the portal the host's Docker socket and, with it, control of the
host. Installing `mkdocs-techdocs-core` in the image avoids that.

## Keep the portal open and read-only

The portal exists to be looked at, and a sign-in wall would stop most visitors at
the door, so anyone can enter as a guest. That only works if a guest can't change
anything, and hiding pages doesn't do that: an early version turned off the
create and import pages, but a guest token could still call the scaffolder API.

Enforcement now lives in the backend. The scaffolder, notifications, user
settings, and MCP plugins aren't installed, and a permission policy denies every
user action except reading. TechDocs still rebuilds pages when they're read,
which writes to its own volume but can't change what they say. Real sign-in comes
back with self-service templates, which need it.

## Publish through a tunnel, with no route out

The host sits on a home network, so opening ports would expose its address and
leave a public service next to private ones. A Cloudflare Tunnel makes an outbound
connection instead, and Cloudflare provides HTTPS.

The tunnel runs as its own container with its own token, so it can't affect the
host's other tunnel, and stopping it takes the portal offline at once. The portal
and Postgres sit on an internal Docker network with no published ports. An
internal network alone still lets containers reach host ports through its
gateway, which a test from inside the container showed, so the gateway is isolated
too. If the portal were compromised, it would have no way to reach the host, the
LAN, the k3s cluster, or the internet. The cost is that anything needing outbound access, such as live
CI status, will need a deliberate exception.

## Publish only the client-facing API

Bramble describes every route for Swagger but turns off its Swagger page in
production, so the full schema isn't public. The portal is public, so its spec
leaves out admin, owner, and metrics routes, keeping the API that Bramble's own
clients already call. The REST spec is generated by registering the server's
routes with stub dependencies and asking `@fastify/swagger` for the document,
rather than written by hand. It's a snapshot, so it needs regenerating when
Bramble's routes change. The gateway has no schema in code, so its AsyncAPI spec is written
from the gateway's opcode and payload types.

Each spec is written into its API entity's file rather than pulled in with
`$text`, because Backstage won't resolve relative paths from a file location, to
keep entities from reading arbitrary files on the host.

## Build the deploys plugin on exported history

The deploys plugin could have called the GitHub API directly, but the portal has
no route to the internet, and opening one for a chart would undo that. Bramble's
repository is also private, so a live integration would need a token able to
read it on a public site. Instead, `scripts/export-deploys.mjs` exports the
deploy workflow's runs with the GitHub CLI, keeping only start times, durations,
and results, and the file ships with the catalog.

A nightly workflow in this repo runs the export and commits new runs. It pulls
rather than having Bramble and Canopy push, because both production deploys run
on a live server, and a push step would need a token that writes to this repo
and could fail a good deploy. Each source repo gets its own fine-grained token
with only Actions: read, since one token can't span two accounts and a classic
token would read every private repo. The host then copies the files from `main`
every 15 minutes into a read-only mount, which the backend reads on each request,
so new runs need no rebuild. A self-hosted runner could have redeployed instead,
but on a public repo that lets outside pull requests run code on the host. The
figures are at most a day old.

A successful run counts as a deploy, and its duration is the time from push to
live, since the workflow starts on push and ends after the deploy step. A failed
run failed its tests or its deploy, so it never reached production. That makes
the failure share a CI measure, not DORA's change failure rate, which counts
deploys that caused problems in production, and the portal labels it that way.
